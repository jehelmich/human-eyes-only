# `benchmark/optical` — M10

Does a real OCR engine read sub-perceptual contrast text, and at what delta does
it stop? That is the whole question. It tests one idea — text placed far enough
below the perceptual threshold that a person cannot see it while staying a clean
signal in the raster — which is the only additive technique in the project that
costs the pixel-reading tier anything.

**It does not measure human visibility**, not partially and not by proxy. "The
machine reads it" and "the person does not see it" are separate measurements and
this suite makes only the first, so treat any recall number as an upper bound on
the technique's value. The `dE00` and `contrast` columns exist to keep that gap
in view: CIEDE2000 is a model prediction for flat patches on a calibrated
display and the WCAG ratio is a threshold rule, so neither is a visibility
measurement. When that measurement is made it uses adopted instrumentation
rather than ours: S-CIELAB at a declared viewing distance and pixel density,
perimetric complexity, FLIP for the pixel diff, MNREAD-derived reading speed,
and ISO/IEC 29170-2's flicker protocol for any shipping decision on something
sub-perceptual. Vision-language models are also out of scope — a different
attacker tier, and one needing an API key and a spend budget.

## Running it

Needs Python 3.9+, **Tesseract** as a system package, and a **Chromium** for
Playwright. Without Tesseract its rows are skipped with a reason; without Chromium
the suite falls back to Pillow, which is a different rasteriser and therefore a
different answer, not an equivalent one.

```bash
cd benchmark/optical
uv venv --python 3.12 .venv          # or: python3 -m venv .venv
VIRTUAL_ENV=.venv uv pip install -r requirements.txt
./.venv/bin/python -m playwright install chromium

./.venv/bin/python -m optical.selftest   # pins the metrics, no pytest
./.venv/bin/python -m optical.run        # full sweep, ~14 min at --jobs 5
./.venv/bin/python -m optical.run --quick
```

`selftest` pins CIEDE2000 to the Sharma reference vectors, because a metric that
drifts produces a plausible table rather than an error. Other flags: `--jobs N`,
`--engines`, `--renderer pillow`, `--limit N`, `--out DIR`, `--keep-images`, and
`--rebuild results/m10.json` to re-emit the report without running OCR again.

## What is swept, and how to read it

Nine per-channel greyscale deltas from 1/255 to 32/255 plus a null and a
maximum-contrast control; white, near-white, mid-grey and near-black backgrounds
with the text lighter or darker wherever there is headroom; 14px sans, 14px serif
and 28px semibold serif; ground truth shaped like the spans HEO protects, carrying
figures and currency. Each sample is scored raw and after one histogram stretch,
and through PNG, JPEG at three qualities, two downscales and a screenshot round
trip.

**The raw-to-norm gap is the number to read first.** A histogram stretch costs an
attacker nothing and needs no suspicion that anything is hidden, so `norm` is the
threat model and `raw` is not. And **digit-token recall, not CER**, is the metric
that matches the defence: a transcript with every word of prose right and the
figure wrong is a total failure that CER scores well. `returned_output` is tracked
separately, because an engine that returns nothing has told the attacker there is
nothing to read and an engine that returns text has not.

The rasteriser is headless Chromium, and the report records the exact build. That
matters more here than anywhere else in the suite: the question is what a
*browser* puts in the framebuffer at a one-level delta, so the answer is a
property of Skia's text rasteriser rather than of the idea. The browser
measurement immediately produced something a pixel histogram could not — **the CSS
delta is not the delta that reaches the raster**, because Chromium's text gamma
emits a glyph mask even where foreground and background are the same CSS colour.

`results/m10.json` and the rendered images are gitignored and regenerated by
rerunning the suite.
